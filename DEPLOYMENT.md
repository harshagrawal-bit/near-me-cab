# Deploying NearMe Cab

Everything below is done once. Budget about **90 minutes**, most of it waiting
for builds.

Three pieces, three places:

| Piece | Where | Cost |
|---|---|---|
| Database | MongoDB Atlas | Free (M0) |
| API | Render — Docker web service | Free with cold starts, or ~₹600/mo |
| Web app | Render — static site | Free, never sleeps |

The repository already contains `render.yaml`, which creates both Render
services for you. You still have to do Atlas by hand, because the connection
string is a secret.

---

## Step 0 — Push to GitHub

Render deploys from a repository, so this comes first.

```bash
cd "/home/harsh/travel app"
git init                     # already done
git add -A
git commit -m "NearMe Cab"
git branch -M main
git remote add origin https://github.com/<you>/nearmecab.git
git push -u origin main
```

**Before pushing, confirm no secrets are going with it:**

```bash
git ls-files | grep -E "\.env$|node_modules|\.venv" && echo "STOP — secrets staged" || echo "clean"
```

`.env` is already in `.gitignore`. `.env.example` *is* committed, and should
be — it documents the variables without their values.

## Step 1 — MongoDB Atlas (15 min)

1. Sign up at **mongodb.com/cloud/atlas** → *Create a free cluster*.
2. Provider **AWS**, region **Mumbai (ap-south-1)**, tier **M0 Free**.
3. **Database Access** → *Add New Database User*.
   - Username `nearmecab`, and use *Autogenerate Secure Password*. **Copy it now** —
     Atlas will not show it again.
   - Role: *Read and write to any database*.
4. **Network Access** → *Add IP Address* → **Allow access from anywhere**
   (`0.0.0.0/0`).

   Render does not publish fixed outbound IPs on the lower plans, so an
   allowlist is not an option here. Your protection is the database password
   and TLS, not the IP filter — which is exactly why the password must be
   the generated one, not something you invented.
5. **Connect** → *Drivers* → copy the connection string. It looks like:

   ```
   mongodb+srv://nearmecab:<password>@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority
   ```

   Replace `<password>` with the real password. If it contains `@`, `/`, `:`
   or `#`, URL-encode those characters or the string will not parse.

Keep this to hand — it is `MONGODB_URI` in the next step.

---

## Step 2 — Render (30 min)

Sign up at **render.com** and connect your GitHub account.

### Create both services

**New → Blueprint** → pick your repository. Render reads `render.yaml` and
offers to create `nearmecab-api` and `nearmecab-web`. Approve it.

The first build will **fail or start unhealthy**, because the environment
variables marked `sync: false` are deliberately not in the repo. That is
expected — fill them in next.

### API service — Environment tab

| Key | Value |
|---|---|
| `MONGODB_URI` | the Atlas string from Step 1 |
| `SEED_ADMIN_EMAIL` | your real admin email |
| `SEED_ADMIN_PASSWORD` | a strong password you choose |
| `CORS_ORIGINS` | `https://nearmecab-web.onrender.com` — see below |
| `GOOGLE_CLIENT_ID` | your OAuth client id |

`JWT_SECRET` is generated by Render automatically. Leave it alone; changing it
signs every user out.

`CORS_ORIGINS` must be the **exact** origin of the web service — scheme, host,
no trailing slash, no wildcard. The API sends credentials, and a wildcard
origin with credentials is rejected by every browser.

### Web service — Environment tab

| Key | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://nearmecab-api.onrender.com` |
| `VITE_GOOGLE_CLIENT_ID` | the same OAuth client id |
| `VITE_BRAND_SUPPORT_PHONE` | your real support number |
| `VITE_BRAND_SUPPORT_EMAIL` | your real support address |

**`VITE_*` variables are compiled into the JavaScript at build time.** Changing
one requires a rebuild, not a restart — use *Manual Deploy → Clear build cache
& deploy*. Nothing secret may ever go in a `VITE_` variable; it ships to every
visitor's browser.

### Chicken and egg

You cannot know either URL until both services exist. So:

1. Deploy both with those two fields blank.
2. Read the real URLs off the Render dashboard.
3. Fill in `CORS_ORIGINS` and `VITE_API_BASE_URL`.
4. Redeploy both.

## Step 3 — Seed the database (5 min)

The database starts empty — no admin account, no routes, no prices. Nobody can
sign in yet.

On the **API service** → *Shell* tab:

```bash
python -m scripts.seed
```

Without `--reset`. That creates the admin, routes, vehicle classes and price
book, and skips anything that already exists.

> `--reset` **deletes every collection first**. Never run it against a database
> with real bookings in it.

Then sign in at `https://nearmecab-web.onrender.com` with the
`SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` you set, and change the password.

---

## Step 4 — Update Google OAuth (5 min)

Your OAuth client currently only trusts `localhost`. In **Google Cloud Console
→ APIs & Services → Credentials → your client → Authorised JavaScript
origins**, add:

```
https://nearmecab-web.onrender.com
```

No redirect URI is needed — this app uses the ID-token flow. Changes take a few
minutes to propagate.

## Step 5 — Verify

```bash
curl https://nearmecab-api.onrender.com/api/health
# {"status":"ok","database":"ok","environment":"production"}

curl https://nearmecab-api.onrender.com/api/auth/providers
# {"password":true,"google":true}
```

Then in a browser:

- [ ] Sign in as admin, see the dashboard
- [ ] Register a customer, book a trip
- [ ] Admin: *Confirm car available* → advance requested
- [ ] Admin: *Mark advance received* → booking confirmed
- [ ] `/driver-signup`, add a vehicle, see the wallet block acceptance
- [ ] Admin funds the wallet → owner accepts the trip
- [ ] **Reload the page while signed in.** If you land on the sign-in screen,
      the refresh cookie is being dropped — recheck `COOKIE_SAMESITE=none`,
      `COOKIE_SECURE=true` and `CORS_ORIGINS`.

## The free tier's one real catch

Render's **free** web service sleeps after 15 minutes of no traffic. The next
request has to boot the container — **40 to 60 seconds** of blank screen.

The static web app never sleeps, so the site loads instantly and then hangs
waiting for the API, which looks broken rather than slow.

The `starter` plan (~₹600/month) removes it. `render.yaml` already specifies
`starter`; change it to `free` if you want to accept the cold start.

Do not try to fix this with an uptime pinger. Render terminates accounts for
it, and it is cheaper to pay for the plan than to lose the service.

## What is NOT set up

Be clear-eyed about these before real customers arrive.

**No backups.** Atlas M0 has none — no snapshots, no point-in-time restore. For
a business whose bookings are its revenue record, this is the reason to move to
M10 (~₹5,000/mo), not storage. Until then, take a manual dump regularly:

```bash
mongodump --uri="<your MONGODB_URI>" --out=backup-$(date +%F)
```

**One server process only.** The rate limiter lives in memory
(`app/core/rate_limit.py`), which is why the Dockerfile runs a single worker.
Scaling to two instances silently weakens login brute-force protection. Moving
it to Redis is the prerequisite for scaling out.

**No error monitoring.** When a customer says "it failed", you will have
nothing to look at. Sentry's free tier is ten minutes of work.

**No online payments.** The 15% advance and driver wallet top-ups are both
recorded by an admin after the money arrives by other means. Razorpay replaces
the manual step; the flow around it is already built and tested.

**Sessions cannot be revoked.** Refresh tokens are stateless JWTs, so signing
out only clears the cookie. A stolen token stays valid until it expires.
